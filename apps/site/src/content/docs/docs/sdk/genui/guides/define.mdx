## Why a DSL

A surface is a flat list of JSON components: fine for a model, tedious for a person. `defineSurface` takes a nested, typed tree instead. Every component is a factory on `ui` whose props autocomplete from the catalog (`ComponentProps`, generated from the same catalog the renderers read), so a misspelt prop or a wrong enum is a type error, and the result is the same flat list an agent would send. ## Write a surface

`ui.Stack(props, children)` nests; the third argument carries what is outside the props: an explicit `id`, `style`, `on`, `visible`, `slots`. A List renders one template per item of a data path: `{ template, path, key }` as its children. `bind(path)` reads the data model (relative inside a template), `call(name, args)` computes, `event(name)` sends an action to you and `run(name, args)` runs a client function.

## Validate and send

`defineSurface` returns a bad surface's problems instead of throwing: `issues` from the same reducer the renderers use (a literal-only prop given a binding, an unknown icon, a missing required prop), the flat `components`, the `messages` (createSurface, updateComponents, one updateDataModel per data path) and their `jsonl`. Hand the messages to any host from the render guides, or embed them in an app template. Ids are assigned top-down (`root`, then `row-1`, `row-2` and so on) unless you name a node.

```ts
const surface = defineSurface(tree, { surfaceId: "working-hours", data: { "/entries": rows } })
if (surface.issues.length) throw new Error(surface.issues.map((i) => i.id + ": " + i.message).join("\n"))
host.receive(surface.messages) // or: transport.send(surface.jsonl)
```
