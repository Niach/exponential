- Un seul champ pour tout : le champ de la page « Agent » lance tout, avec les issues ou une action choisies en haut et l'appareil, l'agent, le modèle et le mode plan en dessous ; la feuille « Start coding » disparaît
- Chaque bouton de lecture y mène : « Start coding » sur une issue, la barre de sélection multiple, « Run » d'une action et « Fix merge conflicts » ouvrent le champ avec la bonne sélection déjà faite
- Des instructions au démarrage : ce que vous tapez à côté des issues ou de l'action choisies arrive à l'exécution comme instructions supplémentaires ; pour un chat, c'est le prompt
- Des images au démarrage : joignez jusqu'à quatre images au champ, la machine les a avant le premier tour
- Les actions ne gardent que des choix : une action demande un dépôt, un board, une pull request ou une icône ; le texte libre vient du champ, avec l'indication de l'action comme texte d'aide
- Les sessions à côté du champ : la page « Agent » liste vos exécutions en cours et passées à côté du prompt, et une exécution lancée par une autre s'affiche imbriquée dessous
- Répondre dans la carte : un plan ou une question se répond dans sa propre carte, avec un champ intégré quand vous préférez écrire plutôt que choisir ; le champ de pilotage s'efface le temps de la carte
- Messages d'agent : un agent peut envoyer une notification à votre équipe via MCP ; elle arrive en notification push et comme sa propre ligne dans l'Inbox
- Des limites cohérentes : un avertissement de quota ne marque plus une exécution comme limitée, et pour une vraie limite, la fenêtre et l'heure de réinitialisation décrivent la même chose
- Limité, pas bloqué : quand un agent épuise son quota en cours d'exécution, la session est marquée comme limitée avec l'heure de réinitialisation, et reste active et pilotable au lieu de se taire
- Champ de pilotage : le champ de session accepte @ pour les coéquipiers, # pour les tickets et : pour les emoji, les trois mêmes que la zone de commentaire
- Modifications en ligne : le diff d'une modification s'affiche sous sa ligne dans la transcription, replié jusqu'à ce que vous le touchiez
- Des groupes d'outils qui disent ce qui s'est passé : une suite repliée d'appels d'outils se lit « 4 commandes exécutées, 2 fichiers modifiés, 1 échec » au lieu d'un simple compte
- Un démarrage voué à l'échec est refusé : démarrer sur une machine dont l'agent n'a plus de quota le signale et indique l'heure de réinitialisation
- Barres de consommation pour un second compte d'agent sur la même machine
- Choix de l'agent : quand un agent n'est pas prêt sur un appareil, le sélecteur le dit et bloque le démarrage tant que vous n'y avez pas lancé le doctor
- Flux de pilotage : les identifiants d'issues comme #EXP-12 deviennent des chips sur lesquelles vous pouvez appuyer, et les commandes de l'agent s'affichent comme des badges de commande
- Relations entre issues : liez des issues comme parent, sous-issue, bloque, bloquée par, doublon ou liée depuis la feuille de propriétés ; taper #EXP-12 dans une description ou un commentaire lie les deux issues tout seul
- Commentaires en fil : répondez sous un commentaire depuis le champ ancré ; les fils restent sur un seul niveau, et un commentaire posté par un agent via MCP l'indique dans son en-tête
- Un premier lancement guidé : créer une équipe vous fait passer par le premier board, les invitations de coéquipiers et la configuration des appareils, dans le même ordre que sur le web et le bureau
- Merge depuis les exécutions d'actions et de chat : une exécution qui a ouvert une pull request affiche « Merge » dans sa vue de pilotage, et Reviews liste ces pull requests sous « Agent runs »
- Les sessions restent sur votre machine : les transcriptions sont stockées sur l'appareil qui les a exécutées, jamais sur le serveur ; les exécutions passées s'ouvrent depuis Devices, Chat et Automations et sont récupérées depuis cet appareil quand il est en ligne
